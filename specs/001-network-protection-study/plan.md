**Branch**: 실제 Git 브랜치 없음 (setup_plan 논리 식별자: `001-network-protection-study`) | **Date**: 2026-11-17 | **Spec**: [spec.md](spec.md)

**Input**: `specs/001-network-protection-study/spec.md` 및 사용자 정정: 세 팀원 각각 별도 Python 클래스 파일에 docstring·주석으로 인계 계약을 내장하며 별도 인계 파일은 만들지 않는다. 대역폭은 10~30 정수 균일 추출이다.

## 추가 확정: 빠른 방법 전용 RSS 4GB

사용자는 세 평가 대상 전략을 알고리즘 worker 하나와 직접 Evaluator 호출로 단순화했다. 부모는 300초와 전체 worker RSS 4GB를 감시한다. Python·입력·라이브러리·최악 공격 평가·LP·캐시를 모두 포함하며 정확 탐색에는 이 메모리 한도를 적용하지 않는다.

이는 이전 평가 프로세스 분리·평가 메모리 제외 결정을 대체한다. 평가별 JSON IPC를 없애고 안전한 기본 제어/결과 채널만 유지한다. 전체 RSS 한도는 십진 4GB=4,000,000,000 bytes이며 초기값이나 평가 메모리를 차감하지 않는다. 정상 반환 후 부모의 공식 재채점은 유지한다. 상세 경계와 관측은 research.md D-005~006을 따른다.

## 전략 중립적 범위 — 최신 결정

팀원은 어떤 방호 전략이든 동일 계약으로 제출할 수 있다. 원문 전략은 참고일 뿐 강제하지 않는다. 공통 코드는 기준선 호출·탐욕/교환 단계·전략별 시간 배분·전략 간 의존성을 제공하지 않는다. 검수도 내부 전략이 아니라 입력 불변성·출력 유효성·공통 점수·시간·메모리·실패 상태만 확인한다. 최종 반환안은 마감 전에 제출하면 되며 탐색 중 평가 호출은 선택이다. 공통 기능 완료는 팀원 구현 제출과 독립적으로 판정한다.

## 배포 파일 단위 — 최신 확정

배포 파일은 맵·가중치·수요·공격 조건·하나의 예산·완전탐색 최적 참조를 함께 담는다. 맵만 생성한 중간 산출물은 정식 배포 시나리오가 아니다. 예산별 파일을 별도로 완성한다. 최적 참조를 읽지 않거나 삭제한다는 팀원 신뢰 가정을 적용하며 별도 보안 시스템은 만들지 않는다. 로더는 최적 참조를 알고리즘 입력에서 제외하고, 평가자는 참조를 보유한 원본을 사용한다. 삭제 사본에서도 실행·채점은 가능하다. 아래 기존 CLI 스모크는 중간 입력 생성 검증이며 정식 배포 파일 제작 흐름은 생성 → 예산 고정 → 완전탐색 완료 → 참조 결합·검증 → 배포로 갱신한다. 미완료 기록은 남기지만 정식 배포본으로 표시하지 않는다.

## Summary

김대건 담당 공통 시나리오·평가·정확 탐색·기록·통합 노트북을 구현한다. 팀원이 자유롭게 선택하는 세 전략은 서로 다른 파일에 고정 시그니처와 설명만 제공하고 본문은 NotImplementedError로 남긴다. 기존 세 골격의 알고리즘 본문은 보존하고 이번 단계에서는 내장 계약만 설계 기준선에 동기화한다.

공통 평가는 연결 성분의 정수 쌍 수를 우선 비교하고 동점에만 전달량 비율을 사용한다. 단일 팀원 파일과 고정 문제은행을 직렬 처리하고 조건·반복별 새 worker 안에 Evaluator와 빈 캐시를 둔다. evaluation-v2의 유리수 인증 또는 제한된 HiGHS 잔차 fallback을 사용하며 v1 bundle은 거부한다. 정상 반환안을 중간 최고 후보로 대체하지 않는다. 시간/메모리 초과는 공식 점수 없이 기록하고 수신·보관된 완료 후보만 진단용으로 남긴다.

## 상태 및 남은 구현 검증 항목

U-001~003은 사용자 확정으로 해소했다. spec.md가 요구사항 기준이다. 공통 실행 환경·입력 준비 완료 후 제출 파일 import 직전부터 최종 반환값이 채점기에 도착할 때까지 300초를 측정한다. 제출 파일 import·클래스 생성·입력 전달·자체 전처리·탐색 중 평가 호출 및 대기·결과 전달을 포함하고, 반환 후 공식 채점은 제외한다. 문제은행은 난수로 미리 생성·저장하고 모든 전략에 동일한 파일을 사용한다. 공식 채점이나 반복 실행 때 시나리오를 새로 생성하지 않는다. 알고리즘 내부에서 난수를 사용하는 전략만 동일 시나리오에서 사전 고정·기록한 전략용 시드 다섯 개로 5회 독립 실행하고, 결정적 전략은 1회 실행한다. 전략용 시드 목록은 문제 생성 시드와 분리하며 본 실험 전에 고정한다. 반복마다 새 상태·빈 평가 캐시와 독립된 300초·4GB 한도를 적용한다. 모든 실행의 점수·상태·시간을 보관하고 성공 실행의 연결률·전달량 비율 각각의 중앙값·최솟값·최댓값, 실행 시간, 전체 성공 횟수를 함께 보고한다. 실패는 누락하거나 0점으로 바꾸지 않고, 최고 실행만 대표 성적으로 선택하거나 두 지표를 가중합하지 않는다. 지표별 요약 통계는 실제 단일 방호안의 점수가 아니다. 성공 실행이 없으면 점수 통계는 비워 둔다. 소형 규모·문제 생성 시드 목록, 중·대형 실측 규모, 장비·버전·실명은 후속 운영 입력이다. 반올림·LP 인증·RSS 감독·시드 API·CLI는 research.md D-001~008과 data-model.md의 v1 운영 계약으로 설계를 확정했다. 사용자 연구 규칙 추가 확정이나 실제 검증 완료를 의미하지 않는다.

팀원은 배정된 Python 파일 하나만 제출한다. 채점기는 직접 입력 로딩·예산 전달·참조 분리·한도 적용·최악 공격 평가·최적해 비교·결과표 생성을 수행한다. 사전 계산 결과·타 실행 평가 캐시 재사용은 신뢰 약속으로 금지하고 조건마다 새 상태를 만든다. 정확 탐색 캐시를 팀원 실행에 공유하지 않는다.

## Technical Context

**Language/Version**: Python >=3.11. 현재 호스트 python3는 3.13.5. 프로젝트 venv 설치·검증 후 실제 버전 고정.

**Primary Dependencies**: NumPy(default_rng), NetworkX(공통 그래프 처리), SciPy(linprog method='highs', sparse); 개발 검증 pytest, nbformat, nbclient, ipykernel. stdlib dataclasses/json/decimal/fractions/multiprocessing/resource 사용.

**Storage**: 버전이 있는 JSON 시나리오·manifest, JSONL 실행 기록, CSV 보고서, .ipynb. 시나리오·환경 정보와 계산 실패도 보관한다.

**Testing**: 단위·수작업 오라클·계약·통합 pytest, 실제 작은 LP, 단순/가지치기 일치, 종료·복구·메모리 측정 시험, 노트북 clean-kernel 실행. 성능 결과는 실제 실행 후에만 기록.

**Target Platform**: Linux 단일 장비 로컬 실행. Colab은 4GB 설정 배경이며 최종 장비는 미정이다. PRoot/Colab 등 실제 실행 환경의 worker 종료·RSS 측정 가능성을 검증해야 한다. 이전 검증 기록과 최신 정책 변경의 재검증을 구분하며 종료/RSS 검수는 실제 환경 근거가 필요하다.

**Project Type**: 로컬 연구 라이브러리 + CLI + 제출용 노트북. HTTP/API 서비스는 없음.

**Performance Goals**: 빠른 방법 조건별 300초, 소형 정확 탐색 방법별 600초, 중·대형 단순 완전탐색 조건별 10800초(3시간) 탐색 예산. deadline 후 후보 채택 금지, 종료 정리 시간은 별도 보고. 다양한 크기의 고정 시나리오를 위해 중·대형 크기 세 개를 실측 선정하며 저장할 모든 실제 그래프의 두 예산 각각 단순 완전탐색 10800초(3시간) 내 완료 근거를 요구한다. 이를 넘는 대형 도전군은 제외한다. 이는 저장 문제별 실측 완료 기준이지 전체 그래프 공간의 최악 수행 시간 보장이 아니다.

**Constraints**: 동시에 실험 조건 1개, 팀원 실행은 부모 감독자와 알고리즘 worker 1개(내부 Evaluator 직접 호출), 각 수치 계산 스레드 1개, 동일 저장 시나리오, 방법별 fresh 평가 캐시. 정확 탐색은 D-004를 따른다. 원문과 사용자 정정 우선. 팀원 알고리즘 대리 구현 금지. 입력은 불변이며 예산 초과 방호안을 정상 해로 제출하지 않는다.

**Scale/Scope**: 소형 n=6,8 지원, 예산 20/40%, 수요 n개, 한 곳 공격 R=0.15 및 격자 0.2. 본 실험 시드와 크기는 명시적 manifest. 이번 단계는 최신 정책과 내장 계약 동기화이며 실제 구현/검증 상태는 tasks.md와 quickstart.md를 따른다.

- 기존 명세·품질 체크리스트의 별도 인계 문서 요구를 최신 사용자 지시로 수정.

## 구현 준비 판정

실제 계획/골격 검사와 미실행 검증 관문은 [구현 준비 검토](checklists/implementation-readiness.md)에 분리했다.

설계 게이트: PASS. 별도 헌법은 없고 명세·사용자 정정에 위배되는 추가 기능은 없다. 모든 구현 결정은 research.md D-001~008, 공통 직렬화·CLI는 data-model.md, 팀원 공개 계약은 세 클래스 내부에 있다. contracts/를 만들지 않는 것은 FR-019의 명시적 예외이며 공통 운영 계약을 기존 설계 문서 안에 둔다.

실행 검증 게이트: 정책 변경 후 재검증 필요. 이전 시험 기록과 evaluation-v2/단일 worker 회귀를 구분하고 LP·/proc·spawn 종료·스레드·노트북은 실제 근거로만 통과 판정한다. 본 실험 입력·장비 규모·장시간 승인·세 팀원 구현은 구현 시작을 막지 않으며 본 실험/최종 제출을 막는 별도 운영 관문이다.

## 구현 순서와 검증 관문

1. 모델·저장·생성·공격 기하를 구현하고 재현성·경계 예제로 검증한다 (FR-002~008).
2. LP·평가·동점·캐시를 구현하고 손계산 기대값과 비교한다 (FR-009~012,025).
3. 정확 탐색과 보수적 상한을 구현하고 완료 결과 일치·미완료 표기를 검증한다 (FR-013~016).
4. 정확 탐색 T022~T028 확인 후 공개 문맥·단일 worker 직접 평가·부모 시간/전체 RSS 감독·단일 파일 채점·반환 검사를 구현한다. 시간 경계·초과 후보 진단 전용·고정 문제은행 반복/집계·기본 결과 채널·실패 행 보존을 검증한다. 평가별 IPC 장애 매트릭스는 범위에서 제외하고 대역은 tests에만 둔다 (FR-017~024,026~027,030~039).
5. 초기 노트북과 결과표를 만들되 미구현 방법을 명시한다. 팀원 실구현 제출 후 최종 전체 노트북을 실행한다 (FR-028~029).
6. 장비에서 규모 확인 후 본 실험 manifest를 고정한다. 장시간 실험은 별도 실행 요청에서 수행하며 계획 단계에서 시작하지 않는다.

## Complexity Tracking

사용자 결정(A)에 따라 명세에는 단일 Python 파일·클래스 제출 등 사용자 확정 필수 기술 제약을 보존한다. 품질 기준은 ‘필수 제약 외 불필요한 구현 세부사항 없음’과 내부 구현 방식의 설계 문서 분리로 명확히 했으며 재검토 결과 두 항목은 충족한다. 구체적 수치 정책/CLI/프로세스 설계는 설계 산출물로 분리했다. 이는 헌법이나 요구사항을 완화하거나 실제 구현 검증을 완료했다는 뜻이 아니다.

운영 규칙 명확화 게이트는 해소했다. 부모는 worker 하나의 시간·전체 RSS를 감독하고 worker 내 공통 평가는 동기 직접 호출한다. 평가 계산 시간도 300초에 포함한다. 기본 안전 제어/결과 채널과 공식 재채점만 유지하며 별도 평가 서비스·웹 계층·DB·병렬 실험 스케줄러는 추가하지 않는다.
